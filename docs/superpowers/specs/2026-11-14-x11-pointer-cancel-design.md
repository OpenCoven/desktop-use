# Scoped X11 pointer cancellation

The owned native experiment reproduced a left button left down after cancellation: the actual xdotool helper held button 1 across 25 ms, the adapter reported CANCELLED and reaped the helper in 3 ms, and the button was still down 100 ms later. The experiment's subsequent button release was manual recovery and is not product cleanup. The retained first-failure packet has SHA256 `09b0cec9a6f11b70b611c64f7dce8a3f06e99d0be90192770cad896473709a7b`.

The correction extends the existing private X11 guardian from PR #45 to an explicit pointer transaction. This implementation choice reuses its qualified connection, pre-exec helper registration, pidfd quiescence and bounded cleanup. A separate generic supervisor would duplicate those guarantees. The original PR #45 head and frozen artifacts remain unchanged; this branch started at current main and advanced to the owned reviewed dependency `986d6ba` before the pointer-only changes.

Native qualification also reproduced an existing same-point click failure on both frozen632 and the initial pointer candidateb8: without tracing or preheld input, the original three-second request timed out and delivered zero clicks. The pinned helper's `mousemove --sync` waits for departure from the original position, including when the requested destination is that position. Remove that wait from this click chain; movement and click still share the helper's ordered X connection, with literal coordinate/button/repeat operands and the original action deadline. This remains one X11 click lifecycle correction, and every pointer/keyboard native gate must be repeated on the rebuilt candidate. Earlier b8 receipts remain evidence for that earlier component only.

The current intended button is armed before the real helper can execute. Cleanup releases that button only when it is currently down and was not initially held. An intended preheld button is restorable only at the unchanged pointer position; otherwise cleanup is explicitly unverified. Unrelated buttons, keyboard state, lock/group state and pointer position are preserved. Successful single/right/double click arguments and repeat behavior remain intact. Same-button concurrent physical input cannot be perfectly attributed on X11's shared logical state; the existing qualification limitation remains explicit.

The pointer path snapshots and verifies button state without depending on unrelated keyboard mapping stability. It uses the same 100 ms cleanup watchdog and 40 ms reap reserve. A new private command `P` carries one validated button number in 1..=5. Pointer replies keep the existing eight-byte bound and use a distinct `0xd2` marker, separate from the keyboard `0xd1` report and every acknowledgement. Public schemaVersion remains 1; `releasedButtons` is an additive fixed count bounded by 5. Existing keyboard reply bytes and fields remain unchanged.

The CLI's X11 click path attaches the qualified guardian to the real ordered movement/click helper command, reports conservative partial/input-start facts, and finishes guardian cleanup after helper quiescence. Unavailable guardians preserve the existing helper route and report failed cleanup as unverified. SDK/MCP sanitization accepts only the bounded new count; missing or invalid pointer cleanup on interrupted actions remains visibly unverified. No private input, raw mapping or helper diagnostic becomes durable output.

Required evidence includes scoped state-model negatives, actual private IPC framing, TypeScript projection/fallback checks, the complete local check and packed consumers, Linux Rust tests, then fresh owned native CLI and SDK/MCP pointer cancellation with the same actual held boundary. Keyboard cancellation regressions remain required on any new frozen candidate. Review and exact-head CI precede delivery through a focused dependent PR; final integration must be rechecked after PR #45 lands.

This change addresses the stuck button. Already injected application events applying after cancellation, fixture startup intermittency, macOS, Wayland, physical-display acceptance and final release pairing remain distinct gates of #21.
