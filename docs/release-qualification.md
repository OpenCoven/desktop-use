# Paired candidate qualification

The candidate workflow is `.github/workflows/release.yml`. It runs on a same-repository `feat/paired-releases-25` push and checks out the exact `github.sha`, avoiding pull-request merge-commit provenance. It packs once, then builds and executes extracted release binaries on macOS 15 ARM64, macOS 15 Intel, Ubuntu 22.04 AMD64 and Ubuntu 22.04 ARM64. Each lane checks the actual OS, architecture and Rust host. Linux receipts retain linked glibc symbols and the 2.35 floor; macOS receipts distinguish a 15.0 deployment target from actual observed execution and record unsigned or ad-hoc Mach-O state. No identity signing or notarization is attempted.

The manifest binds one version and full source commit across the package, native archives and generated identities. GitHub artifact attestations cover the package, each native archive and the manifest. The clean-install runner invokes the existing mandatory `gh attestation verify` path with the trusted workflow source digest and branch ref before extraction and selection. This trusted candidate API does not change the public installer's exact release-tag policy. Installer jobs use Node, npm and gh, disable npm lifecycle scripts and install no desktop helpers. Task-owned PATH sentinels reject and record cargo/rustc/rustup invocation throughout installation and selected-consumer execution; successful receipts require the guards active and zero attempts. This proves those phases without usable Rust commands through their PATH, not that the hosted machine physically lacks globally installed Rust.

Every selected pair is checked through the installed package and actual selected executable. SDK and local MCP health/doctor calls run with explicit native paths and private state. Both MCP protocol revisions, 2025-11-25 and 2026-07-28, must pass. Health execution can succeed while the report truthfully records a missing graphical backend; it does not prove graphical effects, screen-capture grants or installed user-app acceptance.

The initial 0.1.3 candidate has no previous paired release and records update/rollback as not run. After its complete source-bound workflow is verified and archived, a second candidate can add `qualification/release-previous.json` with exactly `runId`, `sourceCommit`, `sourceRef` and `version`. These values identify the earlier successful same-repository push run of this workflow. The runner verifies the GitHub REST run metadata and Git ancestry before downloading its artifacts, then the installer independently re-verifies attestations. The subsequent commit is a version and qualification-input change, not merely a version bump. It must use a separately checked unused 0.1.x version. Qualification stages both real versions and performs previous → current → previous → current; every selection reinstalls the selected packed package and executes native/SDK/MCP consumers. A partial package synchronization stops the run, retains truthful selection state and does not claim successful rollback.

Exact-host lanes pin OpenClaw 2026.4.26 and proposed 2026.11.3 with frozen npm lock integrities and Node 24.22.0. Each lane installs production package dependencies in its own external directory, links only its selected host SDK, verifies the installed package tree, and imports the compiled audit preflight from that installed tree. Receipts include expected and actual versions/integrities, SDK paths/hashes for preflight and loaded plugin, package hash, state root and terminal outcomes. General image/capability lanes use explicit `tools.toolSearch: false` on the newer host so the actual direct full/restricted schemas are exercised; the separate SDK authorization lane retains the newer default dispatcher and tests its real approval lifecycle. Direct-mode schema coverage does not claim default-dispatcher restricted-schema exposure. A failed newer-host lane remains a supported-matrix gap.

Image capture and helper effects in the gateway harness remain synthetic. Those lanes execute the staged release binary for capture decoding, but synthetic capture, deterministic loopback model transport and five-minute approval expiry do not replace native graphical acceptance. The native installed pair, source tests, host compatibility, signing, public release and graphical acceptance are separate evidence classes. Artifact uploads allowlist sanitized JSON receipts and omit gateway configs, raw console logs, histories, credentials and pixels. Candidate manifests describe evidence available when assembled; later installation and gateway receipts do not retroactively rewrite the attested manifest. A final published release requires separately reviewed delivery and evidence reconciliation.

The newer host also distinguishes model tool discovery from authenticated operator HTTP invocation: an explicitly requested plugin tool can expand the HTTP profile while an unchanged minimal model inventory remains empty. Qualification checks the exact successful idle Stop response and same-session audit, then verifies an explicit canonical/legacy deny agent has empty model inventory, HTTP 404 denials, no model tool result, no approval and no executor audit. The minimum host retains its minimal-profile HTTP 404 expectation. Other forbidden tools and trusted action-profile denials remain independently enforced.

An explicit allowlist whose tools are all denied can trigger the pinned host's pre-provider guard. The explicit-deny model check accepts only its exact denied-agent/canonical-and-legacy error with zero incoming provider requests, or one verified no-tool fixture response and its matching assistant completion. The newer host sanitizes its public error, so that path additionally requires exactly one structured private session-lane diagnostic after the turn starts, with the accepted run ID, denied session, turn task kind and exact guard error. Main-lane or unscoped warnings cannot establish this proof, and conflicting or duplicate session records fail it. Only the categorical correlated receipt is uploaded. Generic service errors, different allowlist errors, timeouts, tool calls/results and any provider request on the precheck path fail qualification.

User-denied approvals require the exact response for the pinned host, including the newer host's complete final-denial and fresh-call guidance. Each result must correlate to one requested approval followed by one resolved deny for the same call, tool and session, with no executor audit or prohibited filesystem effect. A run that completes before issuing the expected approval fails immediately with a bounded categorical receipt; the active-run approval deadline is unchanged.

The harness authors every actual qualification prompt with a unique marker. Discovery evidence requires the latest unique qualification marker, exactly one matching tool-name/action declaration after it and one subsequent result with the same normalized ID; prior reuse, ambiguous markers/IDs, conflicting later markers and result-before-call are rejected. Newer-host inserted unmarked user-role context cannot establish a turn or authority by itself. Context budgets, image validation, explicit truncation and history/audit correlation remain separate checks. Future host marker rewrites or replay behavior require fresh proof.

For the pinned newer host and 65536-token fixture context, current discovery text has a 16000-character live cap and an exact context-truncation suffix; a middle-omission marker can occur in the live result. Its chat.history response is separately a display projection capped at 8000 characters. A clipped display result requires explicit display-cap metadata, the accepted run and original tool-call IDs, and a prefix digest matching the verified current provider result. It is labeled chat-history-display, not persisted transcript evidence. Structured assertions still require the original scoped audit and a separately labeled HTTP replay; clipped JSON is never reconstructed or represented as a full model result. The minimum host retains its original provider and persisted-history limits and suffix checks.
