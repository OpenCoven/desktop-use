# Capability contract v1

Doctor and help add `capabilitiesV1` without removing their existing fields or command aliases. The report's `schemaVersion` is exactly 1; consumers must reject unknown major versions. `contracts/v1/capabilities.schema.json` is the common JSON Schema 2020-12 contract. `pnpm run generate:contracts` derives all action keys and the canonical action schema/data from `src/computer-use-actions.ts`; `pnpm run check:contracts` rejects stale generated assets. Edit the schema source rather than the generated schema. Rust embeds the generated action data and needs no Node installation at runtime.

`producer.surface` determines the meaning of an action's availability. The CLI reports eight executable desktop commands; richer host actions, including Stop and local files, retain plugin implementation evidence and `surfaces:["plugin"]`, but their CLI state is `unsupported` with `SURFACE_UNAVAILABLE`. This does not erase their host implementation on headless or unsupported desktop platforms. Desktop commands list `cli` and `plugin` implementations. SDK and MCP surfaces are absent until implemented. A host consumer must apply its own implementation facts and trusted profile rather than treating a CLI-only state as a host policy decision.

`available` means implementation and the reported observational prerequisites exist. `degraded` identifies a reduced behavior such as screenshot-only Linux inspect or page-key scroll fallback. `unverified` keeps unknown access, protocol compatibility, helper versions, mapping prerequisites and effects explicit. `unsupported` identifies a missing implementation, provider, mode, selector or known prerequisite. Permission denial is separate evidence and a fixed reason, not an assertion that the implementation is absent. No availability state proves a desktop effect. Each CLI action includes `actual-action:not-run`; discovery never sends input or captures a screen. Unknown helper versions are null, while the adapter version is known.

Each variant names an explicit mode or null for a non-capture variant, accepted canonical selector properties, provider identity, availability and argument limits. An empty selector list is untargeted behavior. Nonempty lists name the accepted properties for that variant; constraints specify combinations and prerequisites, such as X11 focus requiring wmctrl for combined selectors. Unsupported selector variants are explicit and must never be used as a fallback. `PROVIDER_NOT_SELECTED` means current dispatch precedence selects another installed provider; there is no public provider-selection argument. `mode:auto` is intentionally absent because its scope is not established by this contract. It remains a legacy request behavior with unknown scope where supported.

`limits.parameters` contains machine-readable finite choices and numeric/byte/dimension limits where source establishes them, with `knowledge:unknown` available for facts discovery cannot establish. The `image` entry describes delivered primary-image bounds rather than a request selector; `keyToken` enumerates the case-insensitive tokens used to form ydotool key/chord requests, derived from the same table as dispatch. Screenshot format values use the exact request spellings `png` and `jpg`; inspect emits PNG. Format choices inherit their own variant's state. Grim screenshot variants separate PNG from JPEG: the PNG path follows capture prerequisites, while JPEG additionally needs an established encoding-build fact. When capture prerequisites are available, ordinary doctor/help leaves JPEG `unverified` with `ENCODING_SUPPORT_UNVERIFIED`, `knowledge:unknown` and `GRIM_JPEG_BUILD_SUPPORT_REQUIRED`; it does not infer JPEG support from PATH, a compositor protocol or helper version. A known disabled build reports JPEG `unsupported` with `ENCODING_BUILD_DISABLED`, while capture/provider/protocol failures always remain unsupported even if an encoding is known enabled. No encoding probe or capture is performed during discovery. Image bounds come from the existing decoder constants. JPEG working-memory limits can reject an image below the pixel bound. Coordinates describe desktop pixels; the current root/output extent can impose a tighter bound than the reported numeric maximum. Signed-i32 request syntax does not waive platform bounds. Linux scroll accepts amounts from 1 to 50 and the directions up, down, left and right, with units explicitly distinguished for wheel and key fallback.

`limits.constraints` and `reasonCodes` are fixed codes. Linux inspect carries `NO_SEMANTIC_ELEMENT_IDS`; non-focus app/window/screen/element selectors remain unsupported. Maim window/frontmost capture requires a successful numeric active-window lookup, which doctor does not run. Wayland screen capture needs a compatible capture protocol; the ext-only path remains unknown until helper compatibility is observed. Window/frontmost capture remains unsupported. Wtype needs the virtual-keyboard protocol; otherwise selected ydotool typing is ASCII with active-layout, daemon and uinput prerequisites. Ydotool pointer input keeps the exact package/version, endpoint, output-layout, registration and acceleration constraints from [image geometry](image-geometry.md). Scroll fallback counts page/arrow key presses and never replays failed wheel input. Wayland focus requires Sway IPC and success from the combined literal selector request. Helper presence or a socket variable proves no desktop effect.

Evidence records its kind, status, scope, provider and observation time where meaningful. The report environment normalizes platform to `macos`, `linux`, `windows` or `other`, and session to `x11`, `wayland` or null. A bounded Wayland registry probe is shared with legacy doctor output, with at most two seconds inside the cumulative action deadline; help only inventories paths. MacOS doctor retains the existing Peekaboo permissions request and conservatively reports unknown grants unless a denial is identified. A successful permission process alone does not prove every grant. Discovery does not install helpers, change privacy grants, persist verification history or invoke paid providers.

CLI `policy.profile` is unknown and `gatewayPolicy` is always `not-reported`. Approval requirements describe adapter behavior independently: observation destinations and host file reads may be request-dependent, interactive operations remain required, and diagnostics and same-scope Stop require none. Host configuration and gateway approvals remain host-owned. The Node consumer applies trusted eligibility separately; denial cannot masquerade as backend absence.

The shared concrete fixtures cover macOS unknown/denied/granted access, missing helper, empty/xdotool-only X11 inventories, X11 capture variants, advertised/unavailable/unknown Wayland protocols, grim JPEG unknown/disabled/enabled build facts, headless Linux, Windows and other unsupported platforms. Encoding fixtures supply controlled facts; they do not establish support for a current installation or a successful desktop effect. Rust produces and validates them against the same schema that Node validates, with independent behavioral assertions for backend-specific limits. `UPDATE_CAPABILITIES_FIXTURES=1 cargo test platform_fixtures_validate_schema_and_remain_shared` refreshes fixture reports only after deliberate source/expectation review.

Schema validation is development-only: [jsonschema 0.33.0](https://docs.rs/crate/jsonschema/0.33.0) supports JSON Schema 2020-12 and documents Rust 1.71.1 as its floor; default HTTP/file resolution features are disabled. Its UUID-format dependency is constrained by the exact development pin [uuid 1.18.1](https://docs.rs/crate/uuid/1.18.1/source/Cargo.toml), whose manifest declares Rust 1.63, because current uuid 1.29.2 needs Rust 1.89. The adapter retains Rust 1.88. [Ajv 8.20.0](https://github.com/ajv-validator/ajv/releases/tag/v8.20.0), already present transitively in the baseline lock, is pinned directly for Node tests and uses its documented [2020-12 entrypoint](https://ajv.js.org/json-schema.html). Neither validator is imported by plugin runtime code. Exact dependency integrity is retained in the lockfiles; validator success is contract evidence, not native acceptance.

## Plugin discovery and reference consumer

Plugin `health` and `doctor` add a top-level `capabilitiesV1` plugin report while retaining the legacy result envelope, including the original CLI-relative report inside `result`. `buildPluginCapabilities(adapterEnvelope, hostEvidence, actionPermissions)` validates the adapter report against the bundled v1 schema and overlays the plugin's implementation and a private-origin trusted permission snapshot. Adapter JSON cannot choose a profile, widen eligibility, grant approvals or supply gateway authorization. Every action reports its own profile eligibility and approval requirement; `gatewayPolicy` remains `not-reported`. Stop and local file/shell implementation survive missing adapters, headless sessions and unsupported graphical platforms. Installed clipboard/launch helpers remain unverified until their access and effects are observed; discovery does not execute them.

A report's optional `adapter` records the configured executable, its resolved filesystem path when available, and the adapter-reported version separately from plugin identity. This is the selected adapter's provenance, not generic PATH or Cargo precedence advice. Spawn failure, invalid output/schema and a successfully executed adapter's backend failure have distinct `adapterInvocation.phase` values (`spawn`, `output`, `adapter`). Missing-adapter advice requires spawn ENOENT; adapter-reported ENOENT alone cannot identify a missing executable. Peekaboo helper inventory and explicit matching macOS permission denial can supply backend or privacy guidance. Linux guidance uses its actual `setupGuide` and retains unknown daemon/session access. Successful adapter execution does not receive missing-adapter advice. Audit failures retain `AUDIT_WRITE_FAILED` alongside the original action outcome.

`normalizeCapabilityReport` accepts schema version 1 only and validates the bundled schema using a bounded Node-only runtime validator. Unknown majors produce `CAPABILITY_SCHEMA_UNSUPPORTED`, malformed v1 produces `CAPABILITY_SCHEMA_INVALID`, and health/doctor return a visible error plus an unverified adapter fallback report that preserves local implementation. Legacy adapters without this additive field remain usable but report `ADAPTER_CAPABILITIES_NOT_REPORTED`; they supply no inferred desktop prerequisites. A version migration must ship the new schema and explicit consumer handling together; do not coerce unknown versions to v1. Ajv and Rust jsonschema independently cross-validate the shared concrete fixtures during development; neither is a runtime plugin dependency.

`discoverCapabilityControls(report)` is a host-neutral reference consumer in `src/capabilities.ts`, not an SDK execution surface. It returns one control per canonical action with eligibility, approval, reasons and separate variants containing mode, selectors, provider, parameters and constraints. It enables only allowed actions and available/degraded variants on the producer's surface; unknown profiles, unsupported surfaces and unverified prerequisites stay disabled with reasons. A Stop-only snapshot enables only same-scope Stop and does not authorize a health call. The consumer uses report data without OS-specific branches, preserves PNG/JPEG variants and exposes selector limits rather than inferring support from coarse action readiness.

Packed qualification can run the dedicated synthetic discovery lane with `pnpm exec tsx scripts/qualify-gateway.mjs <fresh-scratch-root> <pinned-openclaw-root> <unpacked-plugin-root> <profile> capabilities`. It checks healthy and failed health/doctor reports, profile ceilings, model-visible schema, legacy Stop and redacted audit through a real disposable gateway. Its controlled reports establish consumer behavior only; they do not establish native grants, desktop effects or image transport. The default `complete` lane retains image/replay, approval, canonical-path, scoped cancellation and audit checks and remains a separate final artifact gate.
